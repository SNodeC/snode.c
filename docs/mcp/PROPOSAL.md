**3. Current MCP obligations.** The current revision is `2026-07-28`. The following distinguishes protocol requirements from proposed server policy.

Modern requests are stateless, including stdio. They carry `params._meta["io.modelcontextprotocol/protocolVersion"]` and `params._meta["io.modelcontextprotocol/clientCapabilities"]`; missing required metadata produces `-32602`, and HTTP 400. Requests use UTF-8 JSON-RPC 2.0, string/integer non-null IDs, and one object rather than batches. Responses preserve readable IDs, contain result or error, and modern results include `resultType`. Notifications have no response. Unknown/unreadable IDs are omitted from modern error responses. No handshake-derived identity or capability may authorize a modern request. [Base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic).

`server/discover` is mandatory on both transports. Its complete result reports `supportedVersions`, `capabilities`, and preferably server identity in `_meta`. The proposed server advertises only implemented tools/resources/prompts. Their enabled families implement `tools/list` and `tools/call`, `resources/list`, `resources/read`, `resources/templates/list`, and `prompts/list`/`prompts/get`; optional completion, sampling, elicitation, task extensions, and protocol logging are not advertised. The first delivery has static registrations. [Discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover), [tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources), [prompts](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts).

Complete discovery/list/resource-read results must include `ttlMs >= 0` and `cacheScope`; use `ttlMs: 0, cacheScope: "private"` initially, avoiding any server cache or freshness promise. Paginated methods can return the entire bounded list without `nextCursor`. [Caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching).

| Binding | Minimal wire requirements and selected behavior |
| --- | --- |
| stdio | Read stdin, write stdout; one compact UTF-8 JSON-RPC object per newline, no literal embedded newline. Stdout contains only MCP messages. Diagnostics may use stderr. No HTTP headers. Client cancellation uses `notifications/cancelled` with `requestId`. Exit promptly at input EOF after bounded cleanup. [stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio.md). |
| Streamable HTTP | One `/mcp` POST endpoint. Each POST carries one request/notification. Clients advertise `application/json` and `text/event-stream` in `Accept`. Request replies use JSON or request-scoped SSE; accepted notification POSTs return empty 202. Validate Origin; an invalid present Origin requires 403. GET/DELETE return 405 in the modern profile; ignore session/replay headers and mint no session IDs. [HTTP binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http.md). |
| POST metadata | `MCP-Protocol-Version` and `Mcp-Method` are required; `Mcp-Name` is required for `tools/call`, `prompts/get`, and `resources/read`, mirroring name/URI. Header names are case-insensitive, values case-sensitive. Decode the exact `=?base64?…?=` sentinel before comparison. Missing/malformed/mismatched required headers produce HTTP 400 and `-32020`. The body remains authoritative. Advertise no `x-mcp-header` annotations initially; if later added, their `Mcp-Param-*` mirrors need the same validation. [Official SDK header reference](https://github.com/modelcontextprotocol/go-sdk/blob/main/docs/protocol.md#http-headers). Notification header requirements are not defined by this revision. [HTTP request metadata](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http.md#request-metadata). |

SSE carries `event: message` with a compact JSON-RPC object in `data`, terminated by a blank line. Send only notifications related to the originating request, followed by its final response; terminate normally afterward. No independent server RPC requests, GET notification stream, SSE IDs, or replay. Include `X-Accel-Buffering: no` as recommended. Client disconnect cancels modern work and prevents further output for that request. [Transport message directions](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports.md), [cancellation](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation), [2026 changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog).

The core also describes subscriptions and multi round-trip requests. A `subscriptions/listen` request receives `notifications/subscriptions/acknowledged` first; acknowledge only supported filters, tag stream messages with `io.modelcontextprotocol/subscriptionId`, and honor cancellation. Static registrations need no list watchers; an empty honored filter is sufficient. No first-release handler requires client input, so it need not initiate an MRTR exchange. If that feature is added later, use `input_required` results and retry input, never a server-initiated RPC. [Message patterns](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns.md), [subscription specification source](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/patterns/subscriptions.mdx).

One specification inconsistency needs qualification: the cancellation page mandates a server-sent cancellation when it tears down a subscription, whereas the subscription page recommends a final successful result for graceful closure. Preserve the required cancellation signal; qualify graceful completion ordering against the contemporary official client before claiming full subscription conformance. This is a protocol qualification issue, not a reason to introduce a separate notification channel.

| Failure | JSON-RPC outcome | HTTP status |
| --- | --- | --- |
| Invalid JSON / envelope | `-32700` / `-32600` | 400, proposed mapping |
| Unknown method, including removed modern `ping` | `-32601` | 404, required |
| Malformed method parameters, missing modern metadata, unknown tool/resource | `-32602` | 400; modern metadata mapping required |
| Required header absent, malformed, or unequal to body | `-32020 HeaderMismatch` | 400, required |
| Required client capability absent | `-32021`, `data.requiredCapabilities` | 400, required |
| Unsupported version | `-32022`, `data.supported` and `data.requested` | 400, required |
| Unexpected server failure | `-32603` | 500 before streaming, proposed mapping |
| Tool execution/input-value failure | A tool result with `isError: true`, not a protocol error | 200 |

These error distinctions follow the [error schema](https://modelcontextprotocol.io/specification/2026-07-28/schema#errors) and [tool error rules](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#error-handling). Modern code must not emit the retired resource-not-found `-32002` or repurpose reserved protocol error numbers. Transport authentication, media-type, and admission errors may use HTTP errors without pretending to be JSON-RPC method results. Proposed media policy: 415 for unsupported content type, 406 for unacceptable response media, 413 for excessive bodies, and 429 for rate-limit rejection.

Use `nlohmann::json`, already required by express ([CMakeLists.txt:44](../../src/express/CMakeLists.txt#L44)). A1 cancels the validator/dependency qualification gate. Implement a small validator inside `mcp-server` for exactly: `type`, `properties`, `required`, boolean `additionalProperties`, `items`, `enum`, `const`, `minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, `maxItems`; annotations `title`, `description`, `default`. Absent `$schema` means 2020-12; an explicit value must identify 2020-12. Reject unsupported keywords, dialects, malformed keyword values, excessive schema depth/size at registration, with a semantic error log and nonzero startup exit. Never advertise an unenforced schema. Validate arguments before invoking a handler. Invalid argument values produce a tool result with `isError: true`; unknown tools and malformed protocol parameters remain JSON-RPC errors. [2026 tool error handling](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#error-handling). This is an intentionally restricted registration API, not general 2020-12 acceptance; document it in the user README.

**Decision:** support `2026-07-28` and `2025-11-25`. Codex demonstrably accepts the latter even though it initially offers June. Supporting June independently is unnecessary for these observed clients. Recheck this on Prompt 2 rather than assuming the binaries remain unchanged.

For 2025 compatibility, implement `initialize`, reply with version/capabilities/serverInfo, accept `notifications/initialized`, and retain `ping`. HTTP initialization can omit the version header; subsequent requests use the negotiated version. Do not require modern `_meta`, `Mcp-Method`, or `Mcp-Name` from that client. GET can return 405. These are version-specific rules, not exceptions to modern header validation. [2025 lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [2025 transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

Legacy HTTP is stateless: no session records, never mint or honor `Mcp-Session-Id`, GET/DELETE return 405, JSON responses only. Accept `initialize`, `notifications/initialized`, and `ping` without weakening modern metadata/header validation. HTTP `notifications/cancelled` returns empty 202 and is ignored for these bounded short operations: the [2025 cancellation handling clause](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation#cancellation-handling) permits ignoring cancellation when the receiver is unable to cancel. Legacy stdio alone owns handshake context in its transport and honors cancellation. No per-connection authorization or capability inheritance for modern requests.

**A. Purpose.** Option 1 (development server alone) provides immediate agent assistance but buries protocol policy in an application. Option 2 (framework plus synthetic demo) is smaller but offers little practical assistance. Approved D1/D3: option 3, reusable module with a read/preview-only development server as its first user. Register exactly `api.find`, `api.read`, `skeleton.preview`, one house-style resource, and one review prompt. No child process, command execution, build/run, config inspection, or file-writing tool.

**B. Placement.** Add `src/mcp/server`, namespace `mcp::server`, following MQTT's module/CMake/install/export layout. Targets: `mcp-server`, `mcp-server-stdio`, `mcp-server-http`, each with `snodec::` alias/export; transport children `stdio` and `http`. Add central component/dependency inventory. Add `src/apps/mcp` executables `snodec-dev-stdio`, `snodec-dev-http` with shared application registrations. The in-tree choice keeps framework improvements, package components, examples and tests together. A separate `SNodeC/snode.c-mcp` repository would require independent release/distribution coordination and is not approved. Preserve existing public API/ABI. Any change to an installed class is a stop/report gate under D1.

**C. Architecture.** One registration, dispatch, schema, cancellation and era-normalization authority. No general RPC engine or second JSON representation. Proposed responsibilities:

| Type | Responsibility |
| --- | --- |
| `Server` | Own static tool/resource/prompt registrations; derive discovery and lists from them; validate and dispatch both protocol eras. |
| `Reply` | One operation's completion, cancellation/deadline and related notifications; at most one terminal result. |
| `stdio::Transport` | Retain protocol fd, observe stdin/output with framework read/write receivers, bound framing and output; legacy handshake context belongs here. |
